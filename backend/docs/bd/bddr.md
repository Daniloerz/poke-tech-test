# Database Decision Records

The schema is created by Liquibase (bootstrap TDR-003). `ddl.sql`, `dml.sql` and `erd.mmd` in this folder are a consolidated copy and must match the changesets.

## BDDR-001 — Table name for users

### Context / Problem

We need a table for the API users. `user` is a reserved word in PostgreSQL.

### Options considered

#### Option A — `"user"` (quoted)
- Natural name.
- Every query must quote it; easy to break; JPA needs extra configuration.

#### Option B — `users`
- Not reserved; common.
- Plural, while the rest of the schema will use singular names.

#### Option C — `app_user`
- Not reserved, singular, and clear about its meaning (users of this application, not Pokemon trainers from the game).

### Decision

Option C, `app_user`. Table names are singular and in `snake_case`.

### Rationale

No quoting, consistent naming.

### Consequences

- Constraint names follow `pk_<table>`, `uk_<table>_<column>`, `ck_<table>_<rule>`, `fk_<table>_<ref>`.

## BDDR-002 — Primary key type

### Context / Problem

Each record needs a unique primary key.

### Options considered

#### Option A — `UUID`
- Can be generated by the client; hard to guess.
- 16 bytes, random index inserts, harder to read in a demo.

#### Option B — `BIGINT GENERATED ALWAYS AS IDENTITY`
- Standard SQL identity, small, ordered, readable (`/users/1`).
- Ids are guessable; this does not matter here because every protected route checks the token, not the id.

### Decision

Option B. `ALWAYS` prevents inserting ids by hand, so the sequence can never be out of sync with the data.

### Rationale

Simple, efficient, and fully supported by Hibernate (`GenerationType.IDENTITY`).

### Consequences

- Seed data does not set ids; the database assigns them (1 and 2 on a clean database).

## BDDR-003 — Case-insensitive unique username

### Context / Problem

`Ash` and `ash` must be the same user (user-auth AC-02), and usernames must be unique.

### Options considered

#### Option A — `citext` column type
- Case-insensitive comparison done by PostgreSQL.
- Needs a PostgreSQL extension; the value keeps the original case, which complicates the domain.

#### Option B — Unique index on `lower(username)`
- Keeps the original case and enforces uniqueness.
- Every query must use `lower(username)` to use the index.

#### Option C — Store in lower case + unique constraint + check constraint
- The application normalizes the username (domain rule); the unique constraint enforces uniqueness; a `CHECK (username = lower(username))` guarantees that no row breaks the rule.
- The original case typed by the user is not kept (acceptable for a username).

### Decision

Option C.

### Rationale

Plain columns and plain queries, no extension. The check constraint is a small duplication of the domain rule, accepted because the uniqueness guarantee depends on it.

### Consequences

- The unique constraint creates the only index needed for login (`WHERE username = ?`); no extra index.

## BDDR-004 — Password hash column

### Context / Problem

We store BCrypt hashes (user-auth TDR-002).

### Options considered

#### Option A — `CHAR(60)` / `VARCHAR(60)`
- Exact size of a BCrypt hash.
- A future change of algorithm (for example Argon2, or a `{bcrypt}` prefix) would need a migration.

#### Option B — `VARCHAR(100)`
- Room for other formats; no real storage cost in PostgreSQL.

### Decision

Option B.

### Rationale

Small margin for a likely future change, at no cost.

### Consequences

- The column name says what it holds (`password_hash`), so nobody expects a plain password.

## BDDR-005 — Timestamps

### Context / Problem

Records need a creation time.

### Options considered

#### Option A — `TIMESTAMP` (without time zone)
- The value depends on the server time zone settings.

#### Option B — `TIMESTAMPTZ` with `DEFAULT now()`
- Stores an absolute instant; maps to `Instant` in Java; filled by the database also for seed rows.

### Decision

Option B.

### Rationale

Absolute instants avoid time-zone bugs between the database, the JVM and the clients.

### Consequences

- Hibernate reads `created_at` back after the insert (database-generated value).

## BDDR-006 — Demo data

### Context / Problem

The exercise asks for seeded data or mock credentials. The data must be loaded automatically and only once.

### Options considered

#### Option A — Java runner at startup (`CommandLineRunner`) that creates users if missing
- Hashes generated at runtime.
- Seed logic hidden in application code; runs on every start; not visible in the SQL docs.

#### Option B — Liquibase SQL changeset with pre-computed BCrypt hashes
- Versioned with the schema, runs once, same SQL as `dml.sql`.
- The hashes are generated once by hand (documented in the changeset).

### Decision

Option B.

### Rationale

One migration mechanism for schema and data, reproducible and easy to review.

### Consequences

- The demo passwords are public (README). They are demo credentials for a local project, not secrets.
- To change a demo password, add a new changeset; never edit an applied one (Liquibase checksums).
